# 工作流与阶段门（Stage Gates）

## 全局状态机
`BACKLOG → READY → IN_PROGRESS → REVIEW → APPROVAL_REQUIRED / BLOCKED → DONE`。仅 `DONE` 可满足下游硬依赖。`REVIEW` 不能自动变成 CEO `APPROVED`。

## G0–G5 阶段
| Gate | 主责 | 可并行协作 | 出口条件 | CEO 决策 |
|---|---|---|---|---|
| G0 市场与立项验证 | 产品经理 | 发行运营、数据分析师 | 可追溯竞品、受众/平台判断、验证风险、MVP 范围提议 | 是否进入设计 |
| G1 核心玩法规格 | 游戏策划 | 程序员、美术、QA | 可试玩的纸面流程、单关状态/线索/失败补救、资源预算 | 是否制作 POC |
| G2 灰盒可玩原型 | 程序员 | 美术、QA、分析师 | 单房间端到端可通关，基本测试通过，有埋点/试玩计划 | 是否投入精修 |
| G3 试玩验证 | QA | 分析师、策划、产品 | Bug 与玩家反馈复盘；继续/修改/放弃建议 | 是否扩展内容 |
| G4 发布准备 | 发行运营 | 程序员、QA、美术 | 平台规则复核、加载性能、隐私、素材和构建检查 | 是否提交审核 |
| G5 运营迭代 | 产品经理 | 分析师、运营、策划、工程 | 基于真实反馈定优先级；迭代风险评估 | 重大范围/资金变化 |

## 调度准则
1. 每个任务 1 名 DRI；协作不限，不能出现两个互相矛盾的最终负责人。
2. 先确定验收标准再执行；缺上游输入，标 `BLOCKED`。
3. G0 中发行预检与分析指标可并行，不强制八人依次启动。
4. G1 可由美术、程序员提供可行性意见；G2 程序和灰盒美术并行，QA 早期参与。
5. 每次交接以任务卡和工件路径为准，禁止全文历史对话传给下一个 Agent。
6. 阶段内日常推进可由 Orchestrator 调度；进入下一 Gate 必须 CEO 显式确认。
7. 若无法真实调用 Agent/本地工具，本规范只是可执行的组织设计，不等于自动后台运行。

## 重大风险上报
平台条款不满足；疑似侵权；预算/周期超限；关键玩法不成立；需采集个人数据；商业 SDK 集成；发布/付款/账号操作。
